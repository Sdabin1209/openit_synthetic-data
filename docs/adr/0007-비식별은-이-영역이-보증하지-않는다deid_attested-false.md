# ADR 0007: 비식별은 이 영역이 보증하지 않는다(deid_attested: false)

상태: 채택 (2026-10-28)

근거 출처 요약: 근거: brief 5절('비식별 전 데이터를 받으면 거부')과 점검 지적 SD-2(점검 문서는 읽지 않음). 게시기가 비식별 여부를 확인할 수단이 없다는 것은 코드에서 확인한 사실이다.

## 맥락
brief는 비식별 전 데이터를 받지 않는다고 하나, 학습 서버에서 가져온 jsonl에는 비식별 증명 필드가 없다(추정 형식). 게시기가 '비식별됨'이라고 보증하면 거짓 보증이 된다.

## 결정
보고서와 매니페스트에 `deid_attested: false`를 항상 적고(비식별 확인 주체는 데이터셋 담당), 이메일·휴대전화·유선전화·주민번호 형태의 의심 패턴을 행 수로만 센다(`pii_suspect`). 기본은 경고, `tolerance.max_pii_suspect_rows`를 정하면 초과 시 거부한다. 패턴 값은 기록하지 않는다.

## 왜 (따른 표준과 근거)
- 확인하지 못한 것을 확인한 것처럼 쓰지 않는다는 워크스페이스 규칙.
- 정규식은 형식 패턴일 뿐이라 이름·주소·병명 같은 식별자는 못 잡는다. 그래서 경고로만 쓴다.
- ReDoS 방지: 모든 수량자에 상한이 있고 중첩 반복이 없다(OWASP ReDoS 지침의 일반 권고를 따름). 행당 검사 길이 20,000자(`PII_SCAN_LIMIT`)는 근거 기록 없음, 데이터 최대 길이를 측정하지 않았다. 적대적 입력 1초 이내 시험이 있다.

## 검토한 대안과 버리는 이유
- 정규식으로 통과/거부 결정: 버린다. 거짓 음성이 있어 안전하다는 인상을 준다.
- NER 기반 검출: 버린다. 의존이 크고 모델 근거가 없다(측정 안 함).
- 비식별 확인을 게시기에 위임하지 않고 문서로만: 버린다. 보고서에 기계적으로 남겨야 사람이 놓치지 않는다.

## 결과
실측(2026-10-28, C1 64,459행): 의심 패턴 0행. 이것은 이메일·전화·주민번호 형태가 없다는 뜻일 뿐 비식별 확인이 아니다(이름·주소 등은 못 본다).

얻는 것: 거짓 보증이 없다. 감수하는 것: 비식별은 여전히 사람·다른 영역의 책임이다.

## 되돌리는 조건
비식별 증명을 입력 데이터가 담아 오면(확인 필드) 그 값을 검증해 기록하는 새 ADR을 쓴다.
