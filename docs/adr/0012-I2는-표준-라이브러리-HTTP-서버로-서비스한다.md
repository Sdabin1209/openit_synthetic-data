# ADR 0012: I2는 표준 라이브러리 HTTP 서버로 서비스한다

상태: 채택 (2026-10-28, D100, D49). 서버 구현(표준 라이브러리 서버, 연결 상한, 헤더 마감)은 ADR 0017이 대체했다. 인증·락·검증·계약 부분은 유효하다

근거 출처 요약: 경로·요청·응답은 `boundary-contracts/HTTP.md` `## I2`가 정본이다. 구조는 model-lab의 I3 서버(model-registry)와 맞췄다. 아래 수치는 모두 측정하지 않았다.

## 맥락
D49는 영역 사이 호출을 HTTP로 정했고 D100은 I2도 그렇게 하기로 했다. 소비자(model-lab)가 이 영역의 코드나 저장소 볼륨을 가져오지 않고 데이터셋을 읽어야 한다.

## 결정
`synthetic_data/service/`에 `http.server.ThreadingHTTPServer` 기반 서버를 둔다. 저장은 기존 `FileDatasetStore`(ADR 0008)를 그대로 쓰고 서버는 얇은 어댑터다.
- 인증: `DATASET_STORE_READ_TOKENS`(역할=토큰), `DATASET_STORE_WRITE_TOKENS`(`synthetic-data=토큰`)를 `read_secret`(D84, `_FILE` 우선)으로 읽는다. 쓰기는 POST만, 쓰기 역할은 synthetic-data 하나. 토큰은 32자 이상(시작 때 검사). 읽기 경로는 읽기·쓰기 토큰 모두 허용한다.
- 멱등·불변: 같은 (id, 버전, content_hash)는 200, 다른 내용은 409, 새 것은 201. 판정은 저장소 계층(ADR 0006)이 한다. 한 번 게시된 버전은 바꾸는 경로가 없다.
- 검증: 게시 본문 tar는 일반 파일만(심볼릭 링크·`..`·절대 경로·중복 이름·`manifest.json`과 `files/` 밖의 항목은 400), 파일 집합 = manifest 경로, 해시·줄 수·스키마·EVAL 누수는 저장소 계층이 확인한다. 읽기 `files/{path}`는 `..`·절대 경로·역슬래시를 400, manifest에 없는 경로를 404로 답한다.
- 자원 한도(값은 환경 변수로 조정, 모두 측정하지 않은 보수적 시작값이다. 출처 없음 = 측정 안 함):
  - 본문 상한 1GiB: 데이터셋이 수천~수만 줄 jsonl(수 MB, ADR 0008)이라는 추정의 큰 여유. 실제 최대 크기는 확인하지 않았다.
  - 소켓 timeout 30초, 동시 연결 32. 동시 게시 8, 동시 다운로드 8: 자원 보호용 상한이고 넘으면 503(재시도 가능). 게시는 아래 데이터셋 락으로 직렬화되므로 이 상한은 정확성이 아니라 디스크·스레드 보호다.
  - 디스크 여유: 본문 tar(n) + 풀어 둔 사본(n) + 저장소 스테이징 사본(n) = 최대 약 3n이 동시에 있으므로 3n + 1GB 미만이면 503. 3n은 코드를 읽어 센 것이고 측정하지 않았다.
  - tar 항목 수 상한 1000: 데이터셋은 파일 6개 안팎이라 큰 여유. inode 고갈 방어. sparse(GNU) 항목과 링크·장치는 거부한다. 이름은 정규형만(`./`, `//`, `..` 거부)이고 컴포넌트가 255바이트를 넘으면 거부한다(대표적 파일 시스템의 이름 한계, 대안 비교 안 함). 경로 충돌(`a`와 `a/b`)은 400.
  - 헤더 수신 마감 10초(`DATASET_STORE_HEADER_DEADLINE`): 첫 바이트부터 헤더 끝까지 총 시간. 소켓 timeout은 recv마다라 바이트를 흘리는 연결(slowloris)을 못 막아서, 소켓 읽기마다 남은 시간을 확인하는 래퍼(`_DeadlineRaw`)를 둔다. 값은 측정 안 함. 유휴 keep-alive 연결은 첫 바이트가 올 때까지 소켓 timeout(30초)만 적용된다. 본문을 천천히 보내는 연결은 소켓 timeout(recv마다)에 의존하며 총 시간 마감은 없다(게시 본문은 클 수 있어 총 시간을 정하는 근거가 없다, 한계).
  - `Content-Length`는 숫자만, 하나만. 아니면 400(요청 밀반입 방어).
- 인증 실패 제한(10회/60초, 측정 안 함): **차단 확인이 인증보다 먼저다.** 차단 중인 주소는 올바른 토큰도 503으로 거부한다. 차단 뒤에도 토큰이 맞는지 알려 주면 제한이 추측을 막지 못하기 때문이다. 차단 중에는 실패를 더 쌓지 않아(deque 길이 ≤ 10) 메모리가 늘지 않고, 창(60초)이 지나면 주소 항목을 지운다. 차단 해제는 차단을 만든 가장 오래된 실패로부터 60초 뒤다. 영향: 같은 주소에서 오는 정상 클라이언트도 그 시간 동안 503을 받는다(호출자는 재시도 가능 오류로 처리). **한계**: 프록시·Docker 네트워크 뒤에서는 호출자가 모두 같은 `client_address`로 보여, 공격자 한 명이 같은 주소의 모든 호출자를 60초씩 막을 수 있다(잘못된 토큰만 보내면 된다). 이 서비스는 내부 네트워크 전용(deploy ADR 0032)이라 수용하고, `X-Forwarded-For`는 신뢰할 수 있는 프록시가 없어 쓰지 않는다. `/healthz`·`/readyz`는 인증 전이라 차단과 무관하다.
- 동시 게시: **데이터셋 ID 단위 락**으로 직렬화한다(같은 ID의 게시는 줄 서고, 다른 데이터셋은 동시에). 같은 버전을 동시에 게시하면 먼저 온 것이 201, 같은 hash는 200, 다른 hash는 409다(전역 1건 직렬화에서는 503이 났다). `existed` 판정을 락 안에서 하므로 저장소의 멱등·충돌 판정과 같은 시점을 본다. 락 단위가 (ID, 버전)이 아니라 ID인 이유: 저장소가 버전 순번(seq)을 데이터셋 디렉터리에서 읽고 쓰는 구간이 있어 같은 데이터셋의 다른 버전 동시 게시가 같은 seq를 받을 수 있다.
- 읽기·다운로드는 파일을 메모리에 올리지 않는다: 해시를 청크로 확인한 뒤 청크로 흘린다(확인과 전송 사이에 파일이 바뀔 수 있으나 버전은 불변이고 쓰기는 이 서버만 한다). tar 묶음은 임시 파일에 만들어 Content-Length를 준다.
- 시작 때 `<root>/datasets/*/.tmp-*`(게시 도중 죽은 잔해)와 `.tmp/`를 지운다. 버전이 하나도 없는 데이터셋 디렉터리는 목록에서 뺀다.
- 쓰기 토큰은 읽기도 허용한다('쓰기 역할은 읽기를 포함'). 계약이 금지하지 않고, 게시자가 자기 게시를 확인하려면 별도 읽기 토큰이 필요 없기 때문이다(deploy gen-secrets도 이 전제). 같은 토큰 값이 읽기와 쓰기에 모두 설정되면 시작을 거부한다(역할 분리가 무의미해진다).
- `/healthz`(살아 있음), `/readyz`(저장 볼륨과 임시 폴더 쓰기 가능). 로그는 표준 출력, 토큰과 본문은 남기지 않는다.

## 왜
- 표준 라이브러리 서버: 의존이 늘지 않고(이미지에 jsonschema와 계약 패키지뿐) 같은 계약 패키지의 I3 서버와 같은 구조라 유지보수가 하나로 모인다. 트래픽은 게시 드물고 읽기는 학습 잡 몇 개라 프레임워크의 성능이 필요하다는 근거가 없다(측정 안 함).
- 토큰 파일과 역할 분리: D84, CONVENTIONS 9절.
- 서버가 검증을 다시 한다: 클라이언트를 믿지 않는다(HTTP.md 공통). 클라이언트 쪽 검증은 오류를 일찍 낼 뿐이다.

## 검토한 대안과 버리는 이유
- FastAPI 등 프레임워크: 버린다. 의존·공급망이 늘고 이 규모에서 얻는 것이 없다. 성능 비교는 측정 안 함.
- 볼륨 공유(SDK 직접 읽기): D49가 금지한다.

## 결과
얻는 것: 계약 클라이언트(`HttpDatasetStore`)와 같은 서버로 시험한다(`tests/test_service_contract.py`). 감수하는 것: 읽기 파일을 메모리(`open_file`)로 올리므로 한 파일이 클 때 메모리를 쓴다(ADR 0008의 파일 구현 한계). TLS는 서비스 간 내부망 전제(D103 L05).

## 되돌리는 조건
데이터셋이 수백 MB 단위로 커지면 스트리밍 읽기와 상한 재측정. 동시 소비자가 늘면 프레임워크·워커를 재검토.

## 보강 (퍼징 시험)

`tests/test_service_fuzz.py`(시드 고정)가 무작위 경로·헤더·메서드·tar 항목을 보내 정의된 코드만 나오는지 본다. HEAD·OPTIONS가 표준 라이브러리 기본 501(HTML)로 답하던 것을 발견해 405로 고쳤다. 모르는 메서드 토큰의 501은 RFC 9110 15.6.2대로 둔다.

## 보강 (2026-10-29, 표준성 점검 D4, 단계 B)
인증 상태 코드를 계약에 맞췄다(`boundary-contracts/CONVENTIONS.md` 9절 '401과 403' 보충 규칙, D106). 토큰이 없거나 틀리거나 스킴이 Bearer가 아니면 **401 + `WWW-Authenticate: Bearer`**, 토큰은 맞지만 권한이 없을 때(읽기 토큰으로 게시)만 **403**이다. 본문 `code`는 둘 다 `PERMISSION_DENIED`이고 클라이언트(`boundary_contracts.clients`)는 둘을 같게 읽으므로 바뀌지 않는다. 근거: RFC 9110 15.5.2(401)·11.6.1(WWW-Authenticate), RFC 6750 3절. 구현은 `service/app.py`의 `Unauthenticated`. `/healthz`·`/readyz`는 인증 없음 그대로다.
인증 실패 속도 제한의 상태 코드는 이미 계약에 맞다: 같은 절의 '과다 요청'이 영역 사이 서비스 API는 429가 아니라 **503 `UNAVAILABLE`**이라고 정한다. 이 서버는 503을 낸다(`Retry-After`는 계약상 서비스마다 다르며 없을 수 있어 싣지 않는다). 역할 부족 403은 실패 횟수에 넣지 않는 기존 동작도 시험으로 고정했다. 재현 시험: `tests/test_service_auth_status.py`(raw HTTP). 속도 제한을 직접 구현한 것(점검 O)은 단계 C 대상이라 이번에 바꾸지 않았다.
