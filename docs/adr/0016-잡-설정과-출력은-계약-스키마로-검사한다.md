# ADR 0016: 잡 설정과 출력은 계약 스키마로 검사한다

상태: 채택 (2026-10-29). ADR 0014의 "허용 목록 `KNOWN_KEYS`로 최상위만 거부"를 대체한다 (Supersedes 0014-결정)

## 맥락
`parse_config`·`parse_import_config`가 키와 형식을 손코드로 검사했다. 중첩 객체(`tolerance`, `split.ratios`, `output.store`)의 모르는 키는 무시돼 오타(`max_invalid_rowz`)가 기본값으로 조용히 돌아갔다. 잡이 stdout·stderr·보고서로 내는 형식은 검사 없이 `asdict`를 찍었다. 헤드가 두 설정과 출력 형식을 계약 스키마(boundary-contracts v2.2.x, D107)로 올렸다.

## 결정
- 설정은 `boundary_contracts.validator("SyntheticJobConfigRun" | "SyntheticJobConfigImport")`로 검사한다(`synthetic_data/contract_check.py`). 스키마로 쓸 수 없는 불변식(비율 합 > 0, 같은 문항 세트의 usage 충돌, 시드 사용 시 failure_store, question_set_id 소속)만 코드에 남긴다.
- 결과 한 줄, `report.json`, `import_report.json`, 설정 오류 한 줄은 내보내기 전에 계약 스키마로 자기 검사한다. 어기면 코드 결함이므로 `AssertionError`로 멈춘다.

## 왜
- 계약이 형식의 정본이면 소비자(deploy)와 생산자가 같은 판정을 쓴다(구조 규칙 R6). 손코드는 두 번째 정본이 되어 어긋난다.
- 스키마가 보증한 것은 다시 검사하지 않는다(R7): 타입, 범위, 열거, `origin`, `pending_policy`, 토큰 값 거부(`token` 키).
- 오류 메시지는 위치와 위반 규칙 이름만 싣고 입력 값은 싣지 않는다(jsonschema 기본 메시지는 값을 싣는다. 표준성 점검 B3).
- 표준: JSON Schema Draft 2020-12(계약 패키지가 정한 방언).

## 검토한 대안
- 손코드 유지 + 시험으로 계약 예시와 대조: 정본이 둘이 되고 중첩 키 거부를 손으로 반복해야 한다. 버린다.
- 출력 검사를 시험에서만: 운영 중 어긋남을 못 잡는다. 검사 비용은 JSON 한 건이라 측정하지 않았고 무시할 수준으로 판단했다(측정 안 함).

## 결과
- 얻는 것: 중첩 모르는 키 거부, 출력 형식 보증, 코드 감소.
- 감수하는 것: 설정 오류 메시지가 jsonschema 규칙 이름 중심이 됐다. 계약 버전이 바뀌면 설정 수용 범위도 같이 바뀐다.

## 되돌리는 조건
계약 스키마가 영역의 실제 설정과 계속 어긋나 `CR`이 반복되면 설정 스키마를 영역 소유로 되돌리는 것을 헤드와 다시 논의한다.
