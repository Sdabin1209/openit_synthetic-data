# ADR 0024: 행 형식은 학습 서버 최종 데이터의 키다

상태: 채택 (2026-11-03). ADR 0003의 행 형식 부분을 대체한다(Supersedes: 0003의 `messages` 형식 서술. 3단계 검증과 값 비노출은 유지).

## 맥락
게시기는 처음에 계약 리포 기록(V2_DRAFT)의 `{messages[system,user,assistant], scenario_id, split, human_review}`를 행 형식으로 가정했고, 2026-10-28에 C1 참조 사본 6개로 맞는다고 확인했다. 2026-11-03 헤드가 학습 서버 최종 데이터(train.jsonl)를 읽기 전용으로 확인한 결과 한 행의 최상위 키는 action, asked_item, canonical_scenario_id, generation, label_source, lora_a_input, lora_a_target, lora_b_input, lora_b_target, next_type, normalizer_plan, pattern_type, previous_turns, question_id, record_type, scenario_family, scenario_id, source, split, style_tag, subtype, user_utterance, validation 이다. 입출력은 `messages`가 아니라 `lora_*_input`/`lora_*_target` 객체다.

## 결정
행에서 `scenario_id`와 역할별 쌍만 읽는다: LORA_A는 `lora_a_input`(ActionExtractionInput)·`lora_a_target`(ActionExtraction), LORA_B는 `lora_b_input`(ResponseRequest)·`lora_b_target`={response_text}(그 문장이 ResponseText). `human_review`는 있으면 싣는다. 나머지 키는 읽지 않는다. `messages` 기반 코드는 지웠다. 파일 이름은 lora_{a,b}_{train,val,test}.jsonl 그대로다(ADR 0002).

## 왜
형식의 정본은 데이터를 만드는 학습 서버이고, 이 영역은 계약 샘플로 옮겨 검증만 한다(ADR 0001). 안 쓰는 키를 무시하면 데이터셋 담당이 키를 더해도 게시기가 깨지지 않는다(읽기 모드, 이전 결정과 같다).

## 검토한 대안과 버리는 이유
- 두 형식을 모두 받기: 쓰이지 않는 옛 형식 코드를 계속 유지해야 하고, 틀린 파일이 조용히 통과할 길이 생긴다. 버린다.
- 23개 키를 모두 필수로 두기: 이 영역이 쓰지 않는 키(validation 등)의 존재까지 요구하게 되어 데이터 쪽 변경에 약해진다. 버린다.

## 결과
얻는 것: 실제 최종 데이터의 키를 그대로 받는다. 감수하는 것: (1) 한 행이 두 역할의 키를 다 담는지, 역할 파일마다 자기 쪽 키만 담는지 확인하지 못해 둘 다 받는다. (2) `human_review`는 확인된 키 목록에 없어 실제 데이터에서는 비어 있을 수 있고, 그러면 pending 정책은 효과가 없다. (3) `validation`·`label_source`의 뜻은 모르고 쓰지 않는다. (4) 새 형식의 실제 파일로는 돌려 보지 않았다(가짜 행 시험만).

## 되돌리는 조건
데이터셋 담당이 형식을 다시 바꾸면 새 ADR로 대체한다.
