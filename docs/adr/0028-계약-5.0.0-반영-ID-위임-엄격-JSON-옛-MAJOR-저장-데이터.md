# ADR 0028: 계약 5.0.0 반영 — ID 형식은 계약에 위임, 입구 JSON은 strict_json, 옛 MAJOR 저장 데이터는 드러낸다

## 상태
채택(2026-11-08). 계약 boundary-contracts v5.0.0(`../boundary-contracts/CHANGELOG.md` 5.0.0). 계약 5.0.1의 `schema_validator`가 나오면 아래 결정 2의 감싸개는 그것으로 바뀐다(새 ADR 또는 이 ADR의 갱신).

## 맥락
계약 5.0.0은 ID 타입을 하나(`_common.$defs.Id`)로 통일하고(D117 '같은 뜻의 타입은 한 번만'), JSON 공통 규칙 구현 `boundary_contracts.strict_json`을 정본으로 두며, `validator()`가 `ContractValidator`(비유한 수 검사를 붙인 감싸개)를 돌려주게 했다. 4.x 저장 데이터는 이전하지 않는다(새 환경 전제, 헤드 결정 2026-11-08). 이 영역은 `schemas/` 파일 11개에 `Id` 패턴 사본(`^[A-Za-z0-9][A-Za-z0-9._:-]*$` + `maxLength 128`)을 갖고 있었고, `RunPlan.question_sets[].id`·`seeds_question_set_id`는 형식이 없었다. 설정·게시 본문의 JSON은 표준 `json.loads`로 읽었다.

## 결정
1. 영역 스키마의 ID 칸은 패턴을 쓰지 않고 `{"type": "string", "x-contract": "_common#/$defs/Id"}`로 계약에 위임한다. `RunPlan.question_sets[].id`, `seeds_question_set_id`(null 허용은 `anyOf [null, Id]`), `SeedPairingInput.fallback_question_set_id`도 같다. `type`을 함께 적는 것은 생성 타입이 `str`이 되게 하려는 것이다.
2. 위임은 `types/schema_registry.py`(생성 파일, `scripts/gen_types.py`)가 푼다. `x-contract` 노드를 계약 스키마 파일의 `$ref`로 바꾸고, 계약의 `schema_registry()`에 영역 스키마를 더한 레지스트리로 검증한다. 검증기는 `ContractValidator`로 감싼다.
3. 설정 파일(`config.py`)과 학습 데이터 행(`import_row_check.py`, 행 한 줄과 안쪽 user·assistant 내용)과 게시 본문 안의 `manifest.json`·샘플 줄(`link_dataset_store_server.py`, `dataset_store.py`)은 `strict_json.loads`로 읽는다.
4. 저장소에 지원하지 않는 `pipeline_schema_version` MAJOR(예: 4)의 매니페스트가 있으면 `get_manifest`가 `UNSUPPORTED_VERSION`으로 거절하고, 서버는 기동 때 한 번 세어 `/readyz`를 503, 사유 코드 `STORE_PIPELINE_MAJOR_UNSUPPORTED`로 낸다. `/healthz`는 영향 없다.
5. 코드 안 거부 조건 하나(`run_job._seed_samples`의 failure_store 없음)를 `schemas/README.md` '스키마 밖 조건' 표 26번에 이유와 함께 적었다.

## 왜
- 결정 1: 계약 5.0.0이 같은 칸을 `Id` 하나로 통일했다. 사본은 계약이 좁아질 때(꼬리 `(?![\s\S])` 같은) 어긋난다. 점검 `head/scripts/check-schema-placement.py`의 D·F가 사본을 위반으로 센다.
- 결정 2: 계약 스키마의 `$id`는 설치 위치의 file URI이고 안정 URI는 5.0.1 예정이라 영역 스키마 파일에 `$ref`를 직접 적을 수 없다. 그래서 파일에는 `x-contract`(이 리포 밖 영역도 쓰는 위임 표지)를 적고 실행할 때 푼다. 감싸개는 계약이 영역이 직접 만든 `Draft202012Validator`를 쓰지 말라고 한 것에 맞춘 임시 조치다(5.0.1 전).
- 결정 3: 같은 규칙(중복 키·NaN·깊이·크기)을 영역마다 구현하면 경계값이 갈린다는 것이 계약 5.0.0 `strict_json`의 근거다. 상한은 계약 기본값(깊이 64, 1 MiB)을 그대로 쓴다. 샘플 한 줄이 1 MiB를 넘는 경우는 측정하지 않았다.
- 결정 4: 4.x 데이터를 조용히 섞어 내보내면 받는 쪽이 MAJOR 불일치로 뒤늦게 거절한다. 계약 5.0.0 '새 환경 전제'는 섞이지 않고 실패하라고 한다. 요청마다 저장소 전체를 읽지 않으려고 기동 때 한 번만 센다(저장소가 기동 뒤에 바뀌는 경우는 `get_manifest`의 거절이 막는다).

- 결정 3의 학습 데이터 행은 **헤드 결정(2026-11-08)**이다. 이 행은 dataset-store를 거쳐 model-lab으로 넘어가는 영역 사이 데이터라 계약 JSON 공통 규칙(CONVENTIONS 10절, I-JSON RFC 7493)의 대상이다. 규칙을 어기는 행은 새 사유 코드를 만들지 않고 기존 `record_json`으로 거른다(사유 문장에 '계약 JSON 규칙 위반 포함'을 더했다).

## 검토한 대안과 버리는 이유
- 스키마 파일에 계약 파일 경로 `$ref`를 직접 적는다: 설치 위치에 따라 달라지는 file URI라 파일이 이식되지 않는다.
- ID 패턴을 영역 스키마에 두고 시험으로 계약과 같음을 지킨다: 사본을 두지 않는다는 규칙(D117)에 어긋난다.
- 옛 MAJOR 데이터를 새 형식으로 이전한다: 헤드 결정이 이전하지 않는 것이다.

## 결과
얻는 것: ID 형식의 정본이 계약 하나다. 설정·게시 입구가 계약 JSON 규칙을 같게 지킨다. 옛 MAJOR 데이터가 드러난다. 감수하는 것: `x-contract`를 푸는 코드가 생성 파일에 있다. 5.0.1에서 바꿀 곳이 한 곳 더 있다.

## 되돌리는 조건
계약이 영역 스키마에서 안정 URI로 `$ref`할 수 있게 하면(5.0.1) `x-contract` 풀이 대신 `$ref`를 파일에 쓰는 새 ADR로 대체한다.
