# ADR 0008: 데이터셋 저장소는 파일 시스템이다(DB가 아니다)

상태: 채택 (2026-10-28)

근거 출처 요약: 근거: brief 7절의 O10('저장소의 실제 기술: 영역이 정한다')과 design.md 12절의 기록('파일 기반, 가볍게', DB 전환은 열려 있음). 성능·용량은 측정하지 않았다.

## 맥락
불변 데이터셋 버전을 쓰고 model-lab이 읽는다. 필요 연산은 게시, 지정 버전 조회, 파일 열기, 버전 목록뿐이다(I2).

## 결정
`FileDatasetStore`: `<root>/<dataset_id>/<version>/{manifest.json, meta.json, files/}`. 임시 디렉터리에 다 쓰고 rename으로 확정한다. 시험용으로 같은 적합성 시험을 통과하는 `MemoryDatasetStore`가 있다.

## 왜 (따른 표준과 근거)
- 데이터셋은 수천~수만 줄의 jsonl 파일(규모는 계약 리포 기록의 행 수, 약 1만 행)이고 한 번 쓰고 읽기만 한다. 질의가 필요 없어 DB의 이점이 적다.
- POSIX rename은 같은 파일 시스템 안에서 원자적이다(POSIX 표준). 읽는 쪽이 반쯤 쓴 버전을 보지 않는다.
- 같은 호스트에서 model-lab이 같은 경로를 읽는다(runbook). 학습 서버가 파일을 읽는 방식과 맞다.

## 검토한 대안과 버리는 이유
- SQLite/PostgreSQL: 버린다. 파일 해시가 매니페스트와 일치해야 하는 불변 산출물이라 파일 그대로가 맞고, 서버 의존이 늘어난다. 성능 비교는 측정 안 함.
- 객체 저장소: 지금은 버린다. 규모가 커지면 후보(design.md 12절의 제안).

## 결과
얻는 것: 의존이 없고 단순하다. 감수하는 것: 여러 호스트 공유와 접근 제어는 파일 시스템에 맡긴다. 동시 게시는 rename 충돌 처리에 의존한다.

## 되돌리는 조건
호스트 사이 공유나 접근 제어가 필요해지거나 규모가 파일 시스템으로 감당되지 않을 때(측정으로 확인).

## 보강 (2026-10-29, 표준성 점검 A3)
게시는 rename의 원자성만 믿고 `fsync`를 하지 않았다. 원자성(읽는 쪽이 반쯤 쓴 버전을 보지 않음)과 내구성(정전 뒤에도 내용이 남음)은 다르다. 이제 임시 디렉터리의 모든 파일과 디렉터리를 `fsync`한 뒤 rename하고, 그 뒤 데이터셋 디렉터리와 저장소 루트를 `fsync`한다(`store/file_store.py`의 `_fsync_tree`). 기대값의 출처: POSIX `fsync(2)`와 원자적 교체 관행(헤드 결정표 D106). rename 뒤 `fsync` 실패는 동시 게시 충돌로 오인하지 않도록 충돌 처리 밖에 둔다. 비용: 게시마다 파일 수만큼 `fsync`(측정 안 함).
재현: 정전은 사용자 공간에서 **재현 못 함**. `tests/test_store_durability.py`가 `os.fsync`·`os.rename` 호출 순서를 가로채 '파일 fsync -> rename -> 디렉터리 fsync'를 확인하고(수정 전 실패), rename 직전 중단(장애 주입)에서 보이는 버전이 없음을 확인한다(수정 전에도 통과: 원자성은 이미 있었다). 같은 hash 재게시가 저장된 파일을 재검증하지 않는 점은 이번에 고치지 않았다(결정표 범위 밖).
