# ADR 0003: 행 검증은 3단계이고 값은 사유에 담지 않는다

상태: 채택 (2026-10-28)

근거 출처 요약: 근거는 계약 리포의 검증 도구(`tools/validate_dataset_v2.py`)가 쓰는 구조와 계약 스키마다. 사유에 값을 넣지 않는 것은 점검 지적(SD-1)에 대한 대응이다. 점검 문서는 이 영역이 읽지 않았고 코디네이터가 전한 설명만 안다.

## 맥락
행 형식은 처음에 추정이었고 C1 실제 파일 6개(64,459행)로 맞는 것을 확인했다(2026-10-28: 모든 행의 키가 human_review, messages, scenario_id, split뿐이고 3단계 검증 실패 0건). 형식은 (`{messages:[system,user,assistant], scenario_id, split, human_review}`, user는 입력 JSON 문자열, assistant는 A는 출력 JSON 문자열/B는 응답 문장). 틀린 행을 사유별로 집계하되 환자 관련일 수 있는 입력 값이 불변 매니페스트와 보고서에 남으면 안 된다.

## 결정
행마다 (1) 구조(`record_*`: 빈 줄, 인코딩, JSON, messages 모양), (2) user를 ActionExtractionInput/ResponseRequest로, assistant를 ActionExtraction/ResponseText로(`input_schema`, `output_schema`), (3) 샘플로 조립해 ActionExtractionSample/ResponseSample로(`sample_schema`) 검증한다. 사유는 `<단계>: <경로>#<스키마 키워드>` 코드뿐이다.

## 왜 (따른 표준과 근거)
- 스키마는 boundary-contracts 패키지의 것을 쓴다(워크스페이스 규칙: 복사본 금지). 1·2단계는 계약 리포의 도구와 같은 분해이고, 3단계는 게시 때 I2 `publish`가 다시 거는 검사와 같은 스키마라 게시 실패를 미리 잡는다.
- 사유를 코드로 제한한 것은 값 비노출 요구다. 검증 시 jsonschema의 메시지에는 입력 값이 들어가므로 쓰지 않는다.

## 검토한 대안과 버리는 이유
- 한 단계(샘플 스키마만): 버린다. 형식 오류와 값 오류를 구분하지 못해 사유 집계가 쓸모없어진다.
- 스키마 메시지를 그대로 기록: 버린다. 입력 값이 섞인다.

## 결과
얻는 것: 사유별 집계로 데이터셋 담당에게 고칠 곳을 알려 줄 수 있다. 감수하는 것: 사유에 값이 없어 어떤 값이 틀렸는지는 줄 번호로 원본을 직접 봐야 한다.

## 되돌리는 조건
다른 빌드에서 실제 행 형식이 달라질 때(1단계를 바꾼다), 또는 계약이 샘플 스키마를 바꿀 때.

## 보강 (2026-10-29, 표준성 점검 B3)
`import`의 행 검증만 값을 싣지 않았고, 게시 단계의 `Validators.boundary`/`survey`와 저장소 `publish`는 jsonschema의 `e.message`(위반한 값이 들어 있다)를 `BoundaryError` 메시지와 `details`에 실었다. 이것이 보고서(`report["error"]`), 종료 시 stderr, dataset-store의 HTTP 오류 본문으로 나갔다. 이제 `schemas._errors`가 `<경로>#<스키마 키워드>`만 낸다. 기대값의 출처: OWASP 로깅·오류 처리(오류에 민감값 비노출)와 이 ADR의 결정. 재현 시험: `tests/test_no_value_leak.py`(잘못된 값을 넣고 메시지·details·HTTP 본문·보고서에 그 값이 없음을 확인). 남은 것: 경로 조각(속성 이름)은 스키마가 정한 이름이라 싣는다. `dataset_id`·`version`·`scenario_id`·`sample_id`는 요청이 보낸 식별자라 그대로 싣는다(발화가 아니다).
